第5章 データベース

お客さんの名前、注文の記録、商品の在庫……。アプリの大事な情報はデータベースに入っています。AWS にはデータベースが十数種類ありますが、「表で管理するか、しないか」で大きく2つに分けると、ぐっと覚えやすくなります。

1. データベースの2大グループ

データベースは、データのしまい方で大きく2つに分かれます。

📒たとえ話：エクセルの表 と 付せんの束
  • リレーショナル（RDB）＝ きっちりした Excel の表。列（名前・住所・電話…）が決まっていて、表と表を「顧客番号」などでつなげて（リレーション）使う。SQL という言葉で検索する。ルールがきびしいぶん、お金の計算などにまちがいが起きにくい。
  • NoSQL＝ 番号つきの付せんの束。「番号（キー）を言えば、その付せんがすぐ出てくる」。付せんごとに書く内容がちがってもOK。決まりがゆるいぶん、ものすごく大量・高速にさばける。

2. 「マネージド」ってなに？

EC2 に自分でデータベースのソフトを入れて使うこともできますが、AWS には面倒なお世話を AWS がやってくれるデータベースがあります。これをマネージドサービスといいます。

🐶たとえ話：ペットホテル

EC2 に自分で入れる＝自宅で犬を飼う（ごはん・散歩・病院、全部自分）。RDS などのマネージド＝ペットホテルにお世話をまかせる。自分は「どんな芸を教えるか（データの中身・使い方）」に集中できる。

やることEC2 に自分で入れるRDS（マネージド）
サーバー・ハードウェアの用意AWSAWS
OS のインストール・パッチ当て自分AWS
データベースソフトの導入・更新自分AWS
バックアップ・障害時の切りかえ自分AWS（設定するだけ）
表の設計・データ・使い方・アクセス権自分自分

※ RDS では、ふつうは中の OS に直接ログインできません（それが必要なら EC2 に自分で入れるか、RDS Custom という特別な形を使います）。

3. RDS と Aurora —— 表で管理するデータベース

Amazon RDSアールディーエス / Relational Database Service
リレーショナルデータベースをマネージドで使えるサービス。中身のソフト（エンジン）は MySQL・PostgreSQL・MariaDB・Oracle・SQL Server・Db2、そして Aurora から選べる。
Amazon Auroraオーロラ
AWS がクラウド向けに作り直した高性能なリレーショナル DB。MySQL・PostgreSQL と互換（同じように使える）。データを3つの AZ に6個コピーして守る。使う量に合わせて自動で伸び縮みする Aurora Serverless もある。
🔑覚え方：RDS のエンジン「マイ・ポス・マリア・オラ・エス・ディー・オーロラ」

「マイポストのマリアが、オラ（スペイン語で こんにちは）とエスディー（SD）カードをオーロラの下で渡す」—— MySQL / PostgreSQL / MariaDB / Oracle / SQL Server / Db2 / Aurora。

マルチAZ と リードレプリカ —— 似ているけど目的がちがう

RDS の試験問題でいちばん出るのがここです。どちらも「コピーを作る」のですが、何のために作るかがちがいます。

🏪たとえ話：お店の「控えの店長」と「案内係」
  • マルチAZ＝ 控えの店長（スタンバイ）。いつも店長と同じことをメモしていて、店長がたおれたらすぐ代わりに店長になる。ふだんはお客さんの相手はしない。→ 目的は止まらないこと（高可用性）。
  • リードレプリカ＝ 質問にだけ答える案内係。商品の場所を聞かれたら答える（読み取り）けど、商品の注文（書き込み）は店長だけ。案内係を増やすと店長がラクになる。→ 目的は速さ（読み取りの負荷分散）。

4. DynamoDB —— 速くて止まらない NoSQL

Amazon DynamoDBダイナモディービー
キーと値（キーバリュー）で管理する NoSQL データベース。サーバーレス（サーバーの台数を考えなくていい）で、どれだけデータが増えても1桁ミリ秒の速さで返す。
🎫たとえ話：巨大なコインロッカー

DynamoDB は、番号（キー）を言えば一瞬で扉が開く巨大コインロッカー。ロッカーが足りなくなったら AWS が勝手に増やしてくれる。ただし「赤い荷物が入っているロッカーを全部探して」のような複雑な探し方は苦手。

おさえるポイント中身
向いている用途ゲームのスコア、ショッピングカート、セッション情報、IoT のデータなど大量・高速なもの
DAXDynamoDB 専用のキャッシュ。ミリ秒→マイクロ秒（1000倍速い単位）に。
グローバルテーブル複数のリージョンに自動でコピーして、世界中どこからでも速く読み書き。
料金の形オンデマンド（使った分だけ）／プロビジョンド（性能を前もって決める）

5. ElastiCache と MemoryDB —— メモリで超高速

Amazon ElastiCacheエラスティキャッシュ
メモリの上にデータを置く、超高速のキャッシュサービス。Valkey・Redis OSS・Memcached が使える。よく読まれるデータを置いて、後ろのデータベースの負担を減らす。
Amazon MemoryDBメモリーディービー
メモリで速いのに、データを複数 AZ にきちんと保存するので、キャッシュではなくメインのデータベースとして使える（Valkey / Redis OSS 互換）。
🗒️たとえ話：机の上のメモ

データベース（RDS）は書庫。毎回書庫まで取りに行くのは時間がかかるので、よく見る情報は机の上にメモ（キャッシュ）しておく。それが ElastiCache。メモなので消えても書庫から取り直せばいい。MemoryDB は「消えないメモ帳」。

ElastiCache でデータベースの前に「メモ」を置く
アプリ（EC2）
→① まずメモを見る
ElastiCacheメモリ・超高速
→② なければ書庫へ
RDS書庫
よく読まれるデータほど、RDS まで行かずに返せる → 速い＆RDS がラク。

6. Redshift —— 分析用の巨大な倉庫

Amazon Redshiftレッドシフト
データウェアハウス（分析専用の巨大なデータベース）。何年分もの売上データを集めて「地域別・月別の売上は？」のような集計・分析を速くこなす。サーバーレス版もある。
OLTP（ふだんの仕事用）OLAP（分析用）
例「注文を1件登録する」「去年の売上を地域別に集計する」
特徴小さい処理を大量に・すばやく大量のデータをまとめて計算
AWSRDS・Aurora・DynamoDBRedshift
📝ことばメモ
データウェアハウス
Data Warehouse ＝ データの倉庫。分析するためにいろいろなデータを集めた場所。DWH と略す。
OLTP
オンライン・トランザクション処理。注文・支払いなど、ふだんの1件1件の処理。
OLAP
オンライン分析処理。たくさんのデータを集計・分析する処理。
列指向
データを「列」ごとにまとめて保存するやり方。「売上の列だけ全部足す」のような集計がとても速い。Redshift はこの方式。

7. 目的別データベースのいろいろ

AWS は「1つのデータベースで全部やる」のではなく、目的ごとに専用のデータベースを使い分ける考え方（目的別データベース）をすすめています。名前と「何用か」を1対1で覚えましょう。

サービス種類何用？（キーワード）
RDS / Auroraリレーショナルふつうの業務システム・EC サイトの注文
DynamoDBキーバリュー大量・高速・サーバーレス
ElastiCacheインメモリキャッシュ・セッション管理
Redshiftデータウェアハウス大量データの分析（OLAP）
DocumentDBドキュメントMongoDB 互換。JSON の形のデータ
Neptuneグラフつながりの分析：SNS の友達関係、おすすめ、不正検知
KeyspacesワイドカラムApache Cassandra 互換
Timestream時系列時間ごとの記録：センサーの温度、サーバーの状態
🔑覚え方：名前からイメージする（イメージ連結）
  • Neptune（海王星）→ 星と星を線でつなぐ星座 → つながり＝グラフ
  • DocumentDB → Document（書類）→ 書類フォルダをモンゴ（Mongo）ルの草原で読む → MongoDB 互換
  • Keyspaces → 鍵（Key）をかけたカサンドラさんの部屋 → Cassandra 互換
  • Timestream → Time（時間）の Stream（流れ）→ 時系列
  • Redshift → 赤い（Red）グラフを並べた分析会議 → データウェアハウス

互換（ごかん）
「同じように使える」こと。MongoDB 互換＝MongoDB 用に作ったアプリが、ほぼそのまま動く。
グラフ（DB の）
折れ線グラフではなく、点（人やモノ）と線（関係）のつながりのこと。
時系列データ
時刻といっしょに記録されていくデータ。「10:00 に 25℃、10:01 に 26℃…」。
インメモリ
データを、ディスクよりずっと速い「メモリ」の上に置くこと。

8. 引っ越し —— DMS と SCT

AWS DMSディーエムエス / Database Migration Service
データベースを AWS へ引っ越す（移行する）サービス。元のデータベースを動かしたまま、データをコピーし続けられるので、止める時間を短くできる。

引っ越し元と先がちがう種類（例：Oracle → Aurora PostgreSQL）のときは、表の設計図（スキーマ）を変換する必要があります。それをするのが SCT（Schema Conversion Tool）、または DMS の中の DMS Schema Conversion です。

ちがう種類のデータベースへの引っ越し
社内
Oracle DB動かしたまま
→① SCT で設計図を変換
DMS
→② DMS でデータを移す
AWS
AuroraPostgreSQL 互換
同じ種類どうし（MySQL → RDS for MySQL）なら、SCT はいらず DMS だけでOK。
🎯試験に出るポイント
  • 「データベースを止まりにくく」「AZ 障害に自動で対応」→ RDS マルチAZ
  • 「読み取りが多くて遅い」→ リードレプリカ か ElastiCache
  • 「サーバー管理なしで、ミリ秒で大量アクセス」→ DynamoDB（さらに速く＝DAX）
  • 「MySQL 互換で、もっと高性能・高可用」→ Aurora
  • 「大量データを分析・集計（BI）」→ Redshift
  • 「つながりの分析（SNS・おすすめ・不正検知）」→ Neptune／「MongoDB を移したい」→ DocumentDB
  • 「データベースを止めずに AWS へ移行」→ DMS（種類がちがえば＋SCT）
⚠️ひっかけ注意
  • マルチAZ は「速くする」ためではない。標準のマルチAZではスタンバイは読み取りに使えない。速さ（読み取り）ならリードレプリカ。
  • RDS はマネージドだが、OS にログインして好きにさわることはできない（ふつうの RDS の場合）。「OS を細かく設定したい」なら EC2 に自分で入れる。
  • DynamoDB は NoSQL。「表どうしを複雑につないで（JOIN して）検索したい」には向かない。

リレーショナルと NoSQL のちがいを、たとえ話で説明すると？
リレーショナル＝きっちりした Excel の表を番号でつなげて SQL で探す。NoSQL＝番号つき付せんの束（キーを言えば一発で出る。形は自由で大量・高速）。
RDS（マネージド）で AWS がやってくれることは？ 自分がやることは？
AWS：ハードウェア、OS・DB ソフトのパッチ、バックアップ、フェイルオーバー。自分：表の設計、データ、使い方、アクセス権。
RDS で選べるエンジンを言えますか？
MySQL・PostgreSQL・MariaDB・Oracle・SQL Server・Db2・Aurora。
マルチAZ とリードレプリカ、それぞれの目的とコピーのしかたは？
マルチAZ＝高可用性（同期コピー、障害時に自動フェイルオーバー）。リードレプリカ＝読み取り性能アップ（非同期コピー、別リージョンも可）。
Aurora の特徴を3つ
MySQL / PostgreSQL 互換、高性能、3つの AZ に6個のコピー（Aurora Serverless もある）。
DynamoDB をさらに速く（マイクロ秒）にする機能は？ 複数リージョンにコピーする機能は？
DAX（DynamoDB Accelerator）。グローバルテーブル。
ElastiCache と MemoryDB のちがいは？
ElastiCache＝消えてもいい「メモ」としてのキャッシュ。MemoryDB＝メモリで速いのに複数 AZ に保存するので、メインのデータベースとして使える。
OLAP（分析）用のデータウェアハウスは？
Amazon Redshift。
Neptune・DocumentDB・Keyspaces・Timestream はそれぞれ何用？
Neptune＝グラフ（つながり）、DocumentDB＝MongoDB 互換のドキュメント、Keyspaces＝Cassandra 互換、Timestream＝時系列。
Oracle から Aurora PostgreSQL へ引っ越すときに使うものは？
SCT（または DMS Schema Conversion）でスキーマを変換し、DMS でデータを移す。
