第5章 データベース

顧客情報、注文履歴、在庫数など、アプリケーションの中核となるデータはデータベースに保存されます。AWS には十数種類のデータベースサービスがありますが、まず「リレーショナルか、NoSQL か」で大きく二分すると、全体を整理しやすくなります。

1. データベースの2分類

データベースは、データの構造と扱い方によって大きく2つに分類されます。

💡イメージで理解する
  • リレーショナル（RDB）：列の定義が厳密に決まった表（テーブル）にデータを格納し、「顧客 ID」などの共通項目で表どうしを関連付けて（リレーション）扱う。問い合わせには SQL を使う。整合性の制約が厳しい分、金銭計算などでデータの矛盾が起きにくい。
  • NoSQL：キーを指定すると対応する値を直接取り出せる形式など、表に限らない構造でデータを扱う。項目ごとに属性が異なっていてもよく、制約が緩い分、大量のデータを高速に処理できる。

2. マネージドサービスとは

EC2 上にデータベースソフトウェアを自分でインストールして運用することもできますが、AWS には運用管理の大部分を AWS が担うデータベースサービスがあります。これをマネージドサービスと呼びます。利用者は、データの設計やアプリケーション側の利用方法に集中できます。

作業EC2 に自分で構築RDS（マネージド）
サーバー・ハードウェアの用意AWSAWS
OS のインストール・パッチ適用利用者AWS
データベースソフトウェアの導入・更新利用者AWS
バックアップ・障害時の切り替え利用者AWS（利用者は設定のみ）
テーブル設計・データ・利用方法・アクセス権利用者利用者

※ 通常の RDS では、基盤となる OS に直接ログインすることはできません。OS レベルの操作が必要な場合は、EC2 上に自分で構築するか、RDS Custom を利用します。

3. RDS と Aurora —— リレーショナルデータベース

Amazon RDSアールディーエス / Relational Database Service
リレーショナルデータベースをマネージドで提供するサービス。データベースエンジンは MySQL・PostgreSQL・MariaDB・Oracle・SQL Server・Db2、および Aurora から選択する。
Amazon Auroraオーロラ
AWS がクラウド向けに設計した高性能なリレーショナルデータベース。MySQL・PostgreSQL と互換性がある。データを3つの AZ に計6つ複製して保護する。負荷に応じて容量が自動で伸縮する Aurora Serverless もある。
🔑覚え方：RDS のエンジンは「OSS 3つ＋商用 3つ＋Aurora」

オープンソース系：MySQL・PostgreSQL・MariaDB ／ 商用系：Oracle・SQL Server・Db2 ／ AWS 独自：Aurora。3＋3＋1 のグループに分けて覚えると漏れが出にくくなります。

マルチ AZ とリードレプリカ —— 似ているが目的が異なる

RDS の出題で最も頻出なのがこの区別です。どちらもデータベースの複製を作る機能ですが、目的が異なります。

💡イメージで理解する
  • マルチ AZ：常に同じ内容を保持している待機系（スタンバイ）を別の AZ に置く。本番系に障害が起きると自動で待機系に切り替わる。待機系は通常時には処理を受け付けない。→ 目的は可用性の向上。
  • リードレプリカ：読み取り専用の複製。参照系の問い合わせを複製側に振り分けることで、本番系の負荷を下げる。書き込みは本番系のみが受け付ける。→ 目的は読み取り性能の向上（負荷分散）。

4. DynamoDB —— 高速・高可用な NoSQL

Amazon DynamoDBダイナモディービー
キーバリュー型（およびドキュメント型）の NoSQL データベース。サーバーレスでサーバー台数を意識する必要がなく、データ量が増えても1桁ミリ秒の応答性能を維持する。

キーを指定した読み書きは極めて高速で、容量やスループットも AWS 側で自動的に拡張されます。一方で、複数のテーブルを結合（JOIN）するような複雑な検索には向いていません。

押さえるべき点内容
適した用途ゲームのスコア、ショッピングカート、セッション情報、IoT データなど大量・高速な読み書き
DAXDynamoDB 専用のインメモリキャッシュ。読み取りの応答をミリ秒からマイクロ秒単位に短縮する。
グローバルテーブル複数リージョンに自動で複製し、各リージョンから低遅延で読み書きできるようにする。
キャパシティモードオンデマンド（リクエスト量に応じた課金）／プロビジョンド（読み書き性能を事前に指定）

5. ElastiCache と MemoryDB —— インメモリデータベース

Amazon ElastiCacheエラスティキャッシュ
データをメモリ上に保持する高速なキャッシュサービス。Valkey・Redis OSS・Memcached に対応。頻繁に参照されるデータを保持し、背後のデータベースの負荷を軽減する。
Amazon MemoryDBメモリーディービー
インメモリの高速性を持ちながら、データを複数の AZ に永続化するため、キャッシュではなくプライマリーデータベースとして利用できる（Valkey / Redis OSS 互換）。

ElastiCache はあくまでキャッシュであり、データが失われても元のデータベースから再取得できることが前提です。MemoryDB は耐久性を備えているため、それ自体を主たるデータ保存先にできます。

ElastiCache をデータベースの前段に置く
アプリケーション（EC2）
→① まずキャッシュを参照
ElastiCacheインメモリ
→② なければ DB へ
RDS元データ
頻繁に読まれるデータほど RDS まで問い合わせずに返せるため、応答が速くなり RDS の負荷も下がります。

6. Redshift —— 分析用のデータウェアハウス

Amazon Redshiftレッドシフト
データウェアハウス（分析専用の大規模データベース）。数年分の売上データなどを集約し、「地域別・月別の売上」のような集計・分析を高速に実行する。サーバーレス版もある。
OLTP（業務処理）OLAP（分析処理）
例「注文を1件登録する」「昨年の売上を地域別に集計する」
特徴小さな処理を大量・高速にこなす大量のデータをまとめて計算する
AWSRDS・Aurora・DynamoDBRedshift
📝用語の補足
データウェアハウス
Data Warehouse。分析を目的として、複数のシステムからデータを集約・蓄積したデータベース。DWH と略す。
OLTP
Online Transaction Processing。注文・決済など、日常業務の個々の処理。
OLAP
Online Analytical Processing。大量のデータを集計・分析する処理。
列指向
データを列単位でまとめて保存する方式。特定の列だけを集計する処理が非常に速い。Redshift が採用している。

7. 目的別データベース

AWS は、1つのデータベースですべてを賄うのではなく、用途ごとに最適なデータベースを使い分ける考え方（目的別データベース）を推奨しています。サービス名と用途を1対1で対応づけて覚えます。

サービス種類用途（キーワード）
RDS / Auroraリレーショナル一般的な業務システム、EC サイトの受注管理
DynamoDBキーバリュー大量・高速・サーバーレス
ElastiCacheインメモリキャッシュ、セッション管理
Redshiftデータウェアハウス大量データの分析（OLAP）
DocumentDBドキュメントMongoDB 互換。JSON 形式のデータ
Neptuneグラフ関係性の分析：SNS の交友関係、レコメンド、不正検知
KeyspacesワイドカラムApache Cassandra 互換
Timestream時系列時刻付きの計測データ：センサー値、サーバーのメトリクス
🔑覚え方：サービス名の意味から用途を連想する
  • Neptune（海王星）→ 天体を線で結ぶ星図 → 関係性＝グラフ
  • DocumentDB → Document（文書）→ JSON 文書を扱う MongoDB 互換
  • Keyspaces → キー空間（Cassandra の用語「keyspace」）→ Cassandra 互換
  • Timestream → Time（時間）の Stream（流れ）→ 時系列
  • Redshift → 大量データを扱うデータウェアハウス（分析用）
📝用語の補足
互換
同じインターフェースで利用できること。MongoDB 互換＝MongoDB 向けに作られたアプリケーションがほぼそのまま動作する。
グラフ（データベースの）
折れ線グラフではなく、ノード（人や物）とエッジ（関係）から成るデータ構造。
時系列データ
時刻とともに記録されていくデータ。例：「10:00 に 25℃、10:01 に 26℃」。
インメモリ
データをディスクより格段に高速なメモリ上に保持すること。

8. データベースの移行 —— DMS と SCT

AWS DMSディーエムエス / Database Migration Service
データベースを AWS へ移行するサービス。移行元を稼働させたまま変更分を継続的に複製できるため、停止時間を最小限に抑えられる。

移行元と移行先でエンジンが異なる場合（例：Oracle → Aurora PostgreSQL）は、スキーマの変換が必要です。これを行うのが SCT（Schema Conversion Tool）、または DMS に統合された DMS Schema Conversion です。

同じエンジンどうし（MySQL → RDS for MySQL）の同種移行であれば、SCT は不要で DMS のみで移行できます。
🎯試験での問われ方
  • 「データベースの可用性を高めたい」「AZ 障害に自動で対処したい」→ RDS マルチ AZ
  • 「読み取りが多く性能が不足している」→ リードレプリカ または ElastiCache
  • 「サーバー管理不要で、ミリ秒単位の応答を大規模に」→ DynamoDB（さらに高速化するなら DAX）
  • 「MySQL 互換で、より高性能・高可用性」→ Aurora
  • 「大量データの分析・集計（BI）」→ Redshift
  • 「関係性の分析（SNS・レコメンド・不正検知）」→ Neptune／「MongoDB を移行したい」→ DocumentDB
  • 「データベースを停止せずに AWS へ移行」→ DMS（エンジンが異なる場合は SCT を併用）
⚠️間違えやすい点
  • マルチ AZ は性能向上のための機能ではありません。標準のマルチ AZ 配置ではスタンバイを読み取りに使えません。読み取り性能の向上にはリードレプリカを使います。
  • RDS はマネージドサービスのため、通常は OS にログインして自由に操作することはできません。OS レベルの細かな設定が必要なら EC2 上に構築します。
  • DynamoDB は NoSQL です。複数テーブルを結合（JOIN）する複雑な検索が必要な要件には適しません。

🧠 想起練習

本文を見ずに答えを思い出してから、各項目を開いて確認してください。

リレーショナルデータベースと NoSQL の違いは？
リレーショナル＝厳密に定義された表を関連付けて SQL で問い合わせる。整合性に強い。NoSQL＝キーバリュー型など表に限らない構造で、スキーマが柔軟で大量・高速な処理に強い。
RDS（マネージド）で AWS が担う作業と、利用者が担う作業は？
AWS：ハードウェア、OS・DB ソフトウェアのパッチ適用、バックアップ、フェイルオーバー。利用者：テーブル設計、データ、利用方法、アクセス権。
RDS で選択できるデータベースエンジンは？
MySQL・PostgreSQL・MariaDB・Oracle・SQL Server・Db2・Aurora。
マルチ AZ とリードレプリカ、それぞれの目的と複製方式は？
マルチ AZ＝高可用性（同期レプリケーション、障害時に自動フェイルオーバー）。リードレプリカ＝読み取り性能の向上（非同期レプリケーション、別リージョンにも配置可）。
Aurora の特徴を3つ挙げると？
MySQL / PostgreSQL 互換、高性能、3つの AZ に計6つのデータ複製（Aurora Serverless もある）。
DynamoDB の読み取りをマイクロ秒単位に高速化する機能は？ 複数リージョンに複製する機能は？
DAX（DynamoDB Accelerator）。グローバルテーブル。
ElastiCache と MemoryDB の違いは？
ElastiCache＝データ消失を前提とするキャッシュ。MemoryDB＝インメモリで高速かつ複数 AZ に永続化するため、プライマリーデータベースとして使える。
OLAP（分析処理）向けのデータウェアハウスサービスは？
Amazon Redshift。
Neptune・DocumentDB・Keyspaces・Timestream の用途はそれぞれ何か。
Neptune＝グラフ（関係性）、DocumentDB＝MongoDB 互換のドキュメント、Keyspaces＝Cassandra 互換、Timestream＝時系列。
Oracle から Aurora PostgreSQL へ移行する際に使うサービスは？
SCT（または DMS Schema Conversion）でスキーマを変換し、DMS でデータを移行する。
