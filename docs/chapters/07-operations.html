第7章 監視・運用・自動化

システムは構築して終わりではなく、監視・記録・再現といった運用が続きます。監視は CloudWatch、操作の記録は CloudTrail、設定の履歴は Config です。環境の再現は CloudFormation です。設計は Well-Architected の6つの柱で評価します。

🧭この章で理解してほしいこと
  • CloudWatch は性能、CloudTrail は操作、Config は設定：共通の Cloud に惑わされない
    • CloudWatch：メトリクスとログを集めて監視する（計器盤と警報）
      • 閾値を超えたらアラームで SNS（通知）や Auto Scaling（台数の増減）を動かす
      • 「CPU 使用率が80%を超えたら通知」の答え
    • CloudTrail：「誰が・いつ・どの API を呼んだか」を記録する
      • 「EC2 を誰が削除したか」「監査のために操作を記録」の答え
    • Config：設定が「いつ・どう変わったか」を記録し、ルール準拠を評価
      • 「設定の変更履歴」「コンプライアンスの継続評価」の答え
      • CloudTrail と組み合わせて調査することも多い
    • Watch＝観察、Trail＝足跡、Config＝設定。英単語がそのまま役割
  • サーバー群の一括管理は Systems Manager：Session Manager なら鍵もポート開放も不要
    • Session Manager：鍵やポート開放なしに、ブラウザから安全に接続する
    • Patch Manager：パッチの適用を一括で自動化する
    • Run Command：複数のサーバーに同じコマンドを一斉に実行する
    • Parameter Store：設定値やパスワードを安全に保管する
  • 環境の再現は構成をコードにする（IaC）：CloudFormation か CDK
    • 手作業の構築は再現に手間がかかり、設定ミスも起きやすい
    • CloudFormation：YAML/JSON のテンプレートどおりに自動構築する
      • 利用は無料。作ったリソースの料金だけかかる
      • スタック：テンプレートから作られたリソースの集合。まとめて削除可
      • 同じテンプレートから開発・本番・別リージョンを同じ構成で作れる
    • CDK：Python や TypeScript で書き、CloudFormation のテンプレートに変換
    • Elastic Beanstalk はコードを渡すと実行環境を自動で用意する PaaS
    • インフラをコードで細かく管理したいなら CloudFormation
  • 点検は Trusted Advisor、障害情報は Health Dashboard：処理が遅い場所は X-Ray
    • Trusted Advisor：環境を自動で点検し、改善点を提案する
      • 分野は6つ：コスト・性能・安全・壊れにくさ・上限・運用
      • 全チェックは Business 以上のサポートプラン
      • 例：全開放（0.0.0.0/0）の SG、S3 の公開、ルートの MFA 無し
    • Health Dashboard：AWS 側の障害・メンテナンスの情報。自分への影響を通知
    • X-Ray：リクエストがどこで時間を使ったかを可視化（分散トレーシング）
    • 「自分のリソースの数値」は CloudWatch、「AWS 側の障害」は Health Dashboard
  • 複数アカウントの管理は3つのサービス：Organizations・Control Tower・Service Catalog
    • Organizations：複数アカウントの一元管理。一括請求と SCP（第2章）
    • Control Tower：整った複数アカウント環境（ランディングゾーン）を自動構築
      • Organizations を基盤に動く
      • 「定石（ベストプラクティス）に沿って自動構築」の答え
    • Service Catalog：承認した構成だけをカタログにして選ばせる
      • 統制を保ちながら、利用者が自分で選んで作れる
  • 設計の評価は Well-Architected の6つの柱：動かす・守る・止めない・速く・安く・優しく
    1. 運用上の優秀性：運用を自動化し、小さな変更を頻繁に行って改善する
    2. セキュリティ：データとシステムを守る（最小権限・暗号化・追跡可能性）
    3. 信頼性：障害から自動で復旧する。「複数 AZ に配置」はこの柱
    4. パフォーマンス効率：要件に合うリソースを選び、効率よく性能を出す
    5. コスト最適化：不要な支出を避け、費用対効果を高める
    6. サステナビリティ：環境負荷を最小化する。2021年に追加された柱
  • Well-Architected Tool は設計の自己評価：設問に答えて無料で評価する
    • Trusted Advisor（実際の環境を自動で点検）とは別物

1. 監視と記録の3サービス：CloudWatch・CloudTrail・Config

名称が似ているため、最も混同しやすい箇所です。3つをひとまとまりとして、「何を対象とするか」の違いで整理します。

💡イメージで理解する
  • CloudWatch：計器盤と警報装置。CPU 使用率などの稼働状況を計測し、異常があれば警報を出します。
  • CloudTrail：操作ログ（監査証跡）。「誰が・いつ・どの操作を行ったか」を記録します。
  • Config：構成管理台帳。リソースの設定が「いつ・どう変わったか」を記録し、社内ルールに準拠しているかを継続的に評価します。
サービス対象答えられる問い
CloudWatch性能・稼働状況（メトリクスやログ）「現在の CPU 使用率は？」「閾値を超えたら通知してほしい」
CloudTrail操作の記録（API の呼び出し）「この EC2 を誰が削除したのか？」
Config設定とその変更履歴「このセキュリティグループの設定はいつ・どのように変わったか？」「ルールに違反した設定はあるか？」
🔑覚え方：英単語の意味から推測する

Watch（観察する）＝稼働状況を観察する。
Trail（足跡・痕跡）＝操作の痕跡が残る。
Config（configuration＝設定）＝設定そのものを記録する。
英語の意味がそのまま役割を表しています。

  • 「設定の変更履歴を残したい」「社内ルールへの準拠状況（コンプライアンス）を継続的に評価したい」→ AWS Config

2. サーバー群の一元管理：Systems Manager

AWS Systems Manager
EC2 やオンプレミスのサーバーを一元的に操作・管理するための機能群。主な機能は次のとおり。
・Session Manager：SSH の鍵管理やポートの開放なしに、ブラウザなどから安全にサーバーへ接続する
・Patch Manager：パッチの適用を一括で自動化する
・Run Command：複数のサーバーに同じコマンドを一斉に実行する
・Parameter Store：設定値やパスワードなどを安全に保管する

3. インフラのコード化：CloudFormation と CDK

マネジメントコンソールで手作業で構築すると、同じ環境の再現に手間がかかり、設定ミスも起こりやすくなります。そこで、インフラ（サーバーやネットワークなどの土台）の構成をコードとして記述し、自動で構築する手法が使われます。これを IaC（Infrastructure as Code）といいます。

💡イメージで理解する

CloudFormation は、建築における設計図と施工の関係に近いものです。設計図（テンプレート）があれば、誰が何度構築しても同じ構成が得られます。テンプレートから作成されたリソースの集合をスタックと呼び、スタック単位でまとめて削除することもできます。

AWS CloudFormation
テンプレート（YAML または JSON）に記述した AWS リソースを自動で構築する。CloudFormation 自体の利用は無料で、作成したリソースの料金のみがかかる。

4. 助言と通知

AWS Trusted Advisor
利用中の AWS 環境を自動で点検し、定石（ベストプラクティス）に基づく改善提案を行う。対象分野はコスト最適化・パフォーマンス・セキュリティ・耐障害性・サービスクォータ（上限）・運用上の優秀性の6つ。すべてのチェック項目を利用するには Business 以上のサポートプランが必要。例：使われていない EBS（コスト）、無制限アクセス（0.0.0.0/0）を許可しているセキュリティグループ・S3 の公開設定・ルートユーザーの MFA 未設定（セキュリティ）。
🔑覚え方：Trusted Advisor の6分野「安く・速く・安全に・壊れず・上限内で・運用よく」

安く＝コスト最適化／速く＝パフォーマンス／安全に＝セキュリティ／壊れず＝耐障害性／上限内で＝サービスクォータ／運用よく＝運用上の優秀性。Well-Architected の柱と重なる項目が多いので、対応づけて覚えると効率的です。

AWS Health Dashboard
AWS 側で発生している障害や予定されたメンテナンスの情報を確認する画面。特に「自分のアカウントのリソースに影響するもの」を通知する。
AWS X-Ray
アプリケーション内でリクエストがどの部品（コンポーネント）を経由し、どこで時間を要したかを可視化する（分散トレーシング）。マイクロサービス構成で、いちばん遅い部分（ボトルネック）を見つけるのに使う。

5. 複数アカウントの管理

AWS Organizations
複数の AWS アカウントを組織として一元管理する。一括請求（請求を 1 つにまとめ、使用量の合算によりボリュームディスカウントを受けやすくなる）と、SCP（サービスコントロールポリシー）による「特定のアカウントでは特定のサービスを使用禁止にする」といった制御ができる。詳しくは 第2章。
AWS Control Tower
セキュリティや統制（ガバナンス）の設定が整った複数アカウント環境（ランディングゾーン）を、ベストプラクティスに沿って自動で構築する。Organizations を基盤として動作する。
AWS Service Catalog
組織が承認した構成だけをカタログとして公開し、利用者はその中から選んで環境を作成する。統制を保ちながらセルフサービスでの利用を可能にする。

6. 設計の指針：Well-Architected フレームワーク

AWS Well-Architected フレームワーク
AWS が多数の事例から体系化した優れた設計のための原則とベストプラクティス。6つの柱で構成される。Well-Architected Tool を使うと、設問に回答する形式で自分のシステム（ワークロード）を評価できる（無料）。
#柱要点
1運用上の優秀性
Operational Excellence		運用を自動化し、小さな変更を頻繁に行いながら継続的に改善する
2セキュリティ
Security		データとシステムを保護する（最小権限・暗号化・追跡可能性）
3信頼性
Reliability		障害から自動的に復旧できるようにする（マルチ AZ・バックアップ）
4パフォーマンス効率
Performance Efficiency		要件に適したリソースを選択し、効率よく性能を引き出す
5コスト最適化
Cost Optimization		不要な支出を避け、費用対効果を高める
6サステナビリティ
Sustainability		エネルギー消費などの環境負荷を最小化する
🔑覚え方：「動かす・守る・止めない・速く・安く・地球に優しく」

動かす＝運用上の優秀性／守る＝セキュリティ／止めない＝信頼性／速く＝パフォーマンス効率／安く＝コスト最適化／地球に優しく＝サステナビリティ。学習方法のページで紹介した「意味のある言葉の並び」で覚える例です。あわせて、6番目のサステナビリティは 2021 年に追加された柱であることも押さえておきます。

🎯試験での問われ方
  • 「RDS や EC2 を複数の AZ に配置する」→ 信頼性の柱（単一障害点をなくす）。コストは上がるのでコスト最適化ではなく、性能も上がらない
  • 「最小権限・暗号化・操作の追跡」→ セキュリティ
  • 「不要な支出を避ける・購入オプションを見直す」→ コスト最適化
  • 「要件に合うインスタンスタイプを選ぶ」→ パフォーマンス効率
⚠️間違えやすい点
  • CloudWatch と CloudTrail：「性能の監視」なら CloudWatch、「誰が操作したか」なら CloudTrail。共通の「Cloud」に惑わされないこと。
  • Config と CloudTrail：Config は「設定がどう変わったか」、CloudTrail は「誰が操作したか」。両者を組み合わせて調査することも多い。
  • Trusted Advisor と Well-Architected Tool：Trusted Advisor は実際の環境を自動で点検し、Well-Architected Tool は設問への回答を通じて設計を見直す。
  • Health Dashboard と CloudWatch：AWS 側の障害情報は Health Dashboard、自分のリソースのメトリクスは CloudWatch。
  • 「無制限アクセスを許可しているセキュリティグループを見つけたい」→ Trusted Advisor。IAM は権限の管理、CloudTrail は操作の記録で、設定の点検はしない。
