1. 監視と記録の3サービス：CloudWatch・CloudTrail・Config

名称が似ているため、最も混同しやすい箇所です。3つをひとまとまりとして、「何を対象とするか」の違いで整理します。

💡イメージで理解する
  • CloudWatch：計器盤と警報装置。CPU 使用率などの稼働状況を計測し、異常があれば警報を出します。
  • CloudTrail：操作ログ（監査証跡）。「誰が・いつ・どの操作を行ったか」を記録します。
  • Config：構成管理台帳。リソースの設定が「いつ・どう変わったか」を記録し、社内ルールに準拠しているかを継続的に評価します。
サービス対象答えられる問い
CloudWatch性能・稼働状況（メトリクスやログ）「現在の CPU 使用率は？」「閾値を超えたら通知してほしい」
CloudTrail操作の記録（API の呼び出し）「この EC2 を誰が削除したのか？」
Config設定とその変更履歴「このセキュリティグループの設定はいつ・どのように変わったか？」「ルールに違反した設定はあるか？」
🔑覚え方：英単語の意味から推測する

Watch（観察する）＝稼働状況を観察する。
Trail（足跡・痕跡）＝操作の痕跡が残る。
Config（configuration＝設定）＝設定そのものを記録する。
英語の意味がそのまま役割を表しています。

2. サーバー群の一元管理：Systems Manager

AWS Systems Manager
EC2 やオンプレミスのサーバーを一元的に操作・管理するための機能群。主な機能は次のとおり。
・Session Manager：SSH の鍵管理やポートの開放なしに、ブラウザなどから安全にサーバーへ接続する
・Patch Manager：パッチの適用を一括で自動化する
・Run Command：複数のサーバーに同じコマンドを一斉に実行する
・Parameter Store：設定値やパスワードなどを安全に保管する

3. インフラのコード化：CloudFormation と CDK

マネジメントコンソールで手作業で構築すると、同じ環境の再現に手間がかかり、設定ミスも起こりやすくなります。そこで、インフラの構成をコードとして記述し、自動で構築する手法が使われます。これを IaC（Infrastructure as Code）といいます。

💡イメージで理解する

CloudFormation は、建築における設計図と施工の関係に近いものです。設計図（テンプレート）があれば、誰が何度構築しても同じ構成が得られます。テンプレートから作成されたリソースの集合をスタックと呼び、スタック単位でまとめて削除することもできます。

AWS CloudFormation
テンプレート（YAML または JSON）に記述した AWS リソースを自動で構築する。CloudFormation 自体の利用は無料で、作成したリソースの料金のみがかかる。

4. 助言と通知

AWS Trusted Advisor
利用中の AWS 環境を自動で点検し、ベストプラクティスに基づく改善提案を行う。対象分野はコスト最適化・パフォーマンス・セキュリティ・耐障害性・サービスクォータ（上限）（加えて運用上の優秀性）。すべてのチェック項目を利用するには Business 以上のサポートプランが必要。
🔑覚え方：Trusted Advisor の5分野「コ・パ・セ・耐・上」

コスト／パフォーマンス／セキュリティ／耐障害性／サービスの上限。Well-Architected の柱と重なる項目が多いので、対応づけて覚えると効率的です。

AWS Health Dashboard
AWS 側で発生している障害や予定されたメンテナンスの情報を確認する画面。特に「自分のアカウントのリソースに影響するもの」を通知する。
AWS X-Ray
アプリケーション内でリクエストがどのコンポーネントを経由し、どこで時間を要したかを可視化する（分散トレーシング）。マイクロサービス構成でのボトルネックの特定に使う。

5. 複数アカウントの管理

AWS Organizations
複数の AWS アカウントを組織として一元管理する。一括請求（請求を 1 つにまとめ、使用量の合算によりボリュームディスカウントを受けやすくなる）と、SCP（サービスコントロールポリシー）による「特定のアカウントでは特定のサービスを使用禁止にする」といった制御ができる。詳しくは 第2章。
AWS Control Tower
セキュリティやガバナンスの設定が整った複数アカウント環境（ランディングゾーン）を、ベストプラクティスに沿って自動で構築する。Organizations を基盤として動作する。
AWS Service Catalog
組織が承認した構成だけをカタログとして公開し、利用者はその中から選んで環境を作成する。統制を保ちながらセルフサービスでの利用を可能にする。

6. 設計の指針：Well-Architected フレームワーク

AWS Well-Architected フレームワーク
AWS が多数の事例から体系化した優れた設計のための原則とベストプラクティス。6つの柱で構成される。Well-Architected Tool を使うと、設問に回答する形式で自分のワークロードを評価できる（無料）。
#柱要点
1運用上の優秀性
Operational Excellence		運用を自動化し、小さな変更を頻繁に行いながら継続的に改善する
2セキュリティ
Security		データとシステムを保護する（最小権限・暗号化・追跡可能性）
3信頼性
Reliability		障害から自動的に復旧できるようにする（マルチ AZ・バックアップ）
4パフォーマンス効率
Performance Efficiency		要件に適したリソースを選択し、効率よく性能を引き出す
5コスト最適化
Cost Optimization		不要な支出を避け、費用対効果を高める
6サステナビリティ
Sustainability		エネルギー消費などの環境負荷を最小化する
🔑覚え方：「運・セ・信・パ・コ・サ」

学習方法のページで紹介した頭字法です。あわせて、6番目のサステナビリティは 2021 年に追加された柱であることも押さえておきます。

⚠️間違えやすい点
  • CloudWatch と CloudTrail：「性能の監視」なら CloudWatch、「誰が操作したか」なら CloudTrail。共通の「Cloud」に惑わされないこと。
  • Config と CloudTrail：Config は「設定がどう変わったか」、CloudTrail は「誰が操作したか」。両者を組み合わせて調査することも多い。
  • Trusted Advisor と Well-Architected Tool：Trusted Advisor は実際の環境を自動で点検し、Well-Architected Tool は設問への回答を通じて設計を見直す。
  • Health Dashboard と CloudWatch：AWS 側の障害情報は Health Dashboard、自分のリソースのメトリクスは CloudWatch。
