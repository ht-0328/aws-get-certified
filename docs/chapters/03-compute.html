第3章 コンピューティング（サーバー）

コンピューティングとは、プログラムを実行する計算資源です。使い方は EC2（仮想サーバー）、コンテナ、Lambda（コードだけ置く）の3つが中心です。同じ EC2 でも購入オプションで料金が大きく変わります。

🧭この章で理解してほしいこと
  • 計算資源は「どこまで自分で管理するか」で選ぶ：EC2 → コンテナ → Lambda の順に楽になる
    • EC2（仮想サーバー）：OS から上をすべて利用者が管理する
    • コンテナ（ECS・EKS・Fargate）：アプリを実行環境ごと管理する
    • Lambda（コードを置くだけ）：コードだけ管理する
    • 「サーバーを管理したくない」「イベントを契機に」→ Lambda
    • 「コンテナだがサーバーは管理したくない」→ Fargate（サーバー不要の実行環境）
  • EC2 は数分で起動できる仮想サーバー：AMI とインスタンスタイプを選んで起動する
    • インスタンス：起動した1台ごとの仮想サーバー（IaaS）
    • カーリースと同じ。車種と初期装備を選び、日々の運用は自分で行う
    • AMI：OS とソフトをまとめた起動用のテンプレート
      • 自作の AMI から同じ構成を何台でも起動できる
    • インスタンスタイプ：CPU 性能やメモリ容量の組み合わせ
      • 名称は m7g.large のように「ファミリー・世代・追加属性・サイズ」
      • 汎用（M・T）、コンピューティング最適化（C）、メモリ最適化（R・X）
      • 高速コンピューティング（P・G など。GPU）、ストレージ最適化（I・D）
    • ディスク：EBS（停止しても残る）とインスタンスストア（停止で消える）
  • 購入オプションは制約が大きいほど安い：中断可ならスポット、長期なら RI・Savings Plans
    • オンデマンド：定価。秒・時間単位で、いつでも使い始め・やめられる
      • 短期間、需要が予測できない、中断が許されない処理、検証用途
    • リザーブドインスタンス（RI）：1年か3年の予約で最大約72%引き
      • インスタンスタイプは固定。常時稼働のデータベースなど
    • Savings Plans：1時間あたりの利用額を1年か3年コミット。最大約72%引き
      • インスタンスタイプやリージョンを変えられる（RI より柔軟）
      • Fargate・Lambda にも適用できる
    • スポット：AWS の余剰を最大約90%引きで使う
      • AWS の都合で2分前の通知で中断される
      • バッチやテストなど、中断されても再実行できる処理だけに使う
      • 「中断できない重要な処理を最も安く」にスポットは誤り
    • Dedicated Hosts：物理サーバーの専有。割高
      • ライセンスの持ち込み（BYOL）や、規制で共有できない場合
      • Dedicated Instances（配置管理はできない）と混同しない
  • ELB は振り分け、Auto Scaling は台数の増減：2つの AZ と組めば高可用性と伸縮性を両立
    • ELB：受けた通信を複数のサーバーに振り分ける（負荷分散）
    • ELB はヘルスチェックで、異常のあるサーバーには送らない
    • ALB：HTTP の内容（URL のパス）で振り分ける。レイヤー7
    • NLB：TCP/UDP を超高速に処理し、固定 IP を持てる。レイヤー4
    • GWLB：サードパーティのセキュリティ製品に通信を経由させる
    • Auto Scaling：需要に応じて EC2 の台数を自動で増減する
      • 異常のあるインスタンスを自動で置き換える
      • 方式はターゲット追跡（CPU 50%を維持）・スケジュール・予測
    • 一方の AZ が止まっても ELB が他方へ振り分け、台数は自動で補う
  • Lambda はイベントのたびに動き、動いた分だけ払う：サーバー管理は不要。1回は最大15分
    • 例：S3 にアップロードされた画像を自動で縮小する（イベント駆動）
    • 課金は実行回数と実行時間（ミリ秒単位）。動かなければ無料
    • EC2 は常時点灯の照明、Lambda は人感センサー付きの照明
    • 数時間かかる処理は EC2・Batch・Fargate で行う
  • コンテナは ECR → ECS/EKS → EC2 か Fargate：保管 → 管理 → 実行環境の役割分担
    • コンテナ：アプリと実行に必要な要素を1つにまとめたもの
    • 規格が統一されているので「手元では動くが本番では動かない」が減る
    • ECR（Registry）：コンテナイメージを保管するレジストリ
    • ECS（Container）：AWS 独自のコンテナ管理。設定が比較的簡単
    • EKS（Kubernetes）：Kubernetes のマネージドサービス
    • Fargate：コンテナを動かすサーバーを AWS が管理する実行環境
      • ECS・EKS と組み合わせると EC2 の管理が不要になる
  • その他は Lightsail・Beanstalk・Batch・Outposts：手軽さ・自動構築・バッチ・自社設置
    • Lightsail：月額定額の簡易サーバー。小規模サイトや WordPress 向け
    • Elastic Beanstalk：Web アプリの実行環境を自動で用意する PaaS
      • コードを渡すと、裏で EC2・ELB・Auto Scaling を作り、置いて動かす
      • EC2 には OS・言語（Java など）・Web サーバーが入った状態で用意される
      • 利用者が用意するのはアプリ本体（Java なら JAR や WAR）だけ
    • Batch：大量のバッチ処理を自動で実行する。スポットと相性がよい
    • Outposts：AWS のハードウェアを自社データセンターに置く
      • AWS と同じサービスや API を使える（ハイブリッド構成）
      • 「データをオンプレミスに置いたまま AWS を使いたい」の答え

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

右に進むほど AWS の管理範囲が広がり、利用者の運用負担は小さくなります。第2章の責任共有モデルと対応させて理解してください。

1. EC2：仮想サーバー

Amazon EC2イーシーツー／Elastic Compute Cloud
数分で起動できる仮想サーバーを提供するサービス。OS 以上の層を利用者が自由に構成できる（IaaS）。起動した1台ごとの仮想サーバーをインスタンスと呼ぶ。
💡イメージで理解する

EC2 はカーリースに近い仕組みです。車種（インスタンスタイプ）と初期装備（AMI）を選んで借り、日々の運用（OS の更新やソフトウェアの管理）は利用者が行います。

AMI：サーバーのテンプレート

AMI は、OS と必要なソフトウェアをまとめたインスタンス起動用のテンプレートです。独自に作成した AMI から、同じ構成のインスタンスを何台でも起動できます。

インスタンスタイプ

CPU 性能やメモリ容量など、用途に応じて選択します。名称は m7g.large のように「ファミリー・世代・追加属性・サイズ」で構成されています。

ファミリー適した用途代表的な記号特徴
汎用Web サーバーなど、バランスの取れた用途M・TCPU・メモリ・ネットワークが均衡
コンピューティング最適化CPU 負荷の高い計算処理C（Compute）CPU 性能を重視
メモリ最適化大量のデータをメモリ上で処理R（RAM）・Xメモリ容量を重視
高速コンピューティング機械学習・画像処理（GPU などを利用）P・G・Inf・Trn専用の演算装置を搭載
ストレージ最適化ディスクへの大量の読み書きI・D高速なローカルストレージ

ストレージは2種類

EC2 には通常 EBS（詳細は第4章）を接続します。ネットワーク経由で接続されるディスクで、インスタンスを停止してもデータは保持されます。一方、インスタンスストアは物理ホストに直結した高速なディスクですが、インスタンスを停止・終了するとデータは消去されます（一時データ向け）。

2. EC2 の購入オプション

同じ EC2 でも、購入オプションによって料金は大きく変わります。試験でも頻出の分野です。

💡イメージで理解する

ホテルの料金体系に置き換えると、次のように整理できます。

  • オンデマンド＝ 正規料金での当日宿泊。いつでも利用・解約できるが割引はない。
  • リザーブドインスタンス（RI）＝ 1年・3年の長期契約。部屋の種類（インスタンスタイプ）は固定される代わりに大幅に割り引かれる。
  • Savings Plans＝ 1時間あたりの利用金額を確約する契約。部屋の種類を変更できるため RI より柔軟。
  • スポットインスタンス＝ 空室の大幅割引。ただし需要が高まると2分前の通知で中断される。
  • Dedicated Hosts＝ 建物（物理サーバー）全体の専有。
購入オプション割引適した用途
オンデマンドなし（正規料金）
秒単位・時間単位の課金		短期間・需要が予測できない・中断が許されない処理。検証用途。
リザーブドインスタンス最大 約72%1年または3年、継続的に稼働することが確定している処理（例：常時稼働のデータベース）。
Savings Plans最大 約72%1年または3年の利用金額を確約する。Compute Savings Plans はインスタンスタイプやリージョンを問わず、Fargate・Lambda にも適用できる柔軟性がある。
スポットインスタンス最大 約90%中断されても再実行できる処理（バッチ処理・テストなど）。
Dedicated Hostsなし（割高）物理サーバーを専有する。既存のソフトウェアライセンス（物理サーバー単位の契約）を持ち込む場合や、規制上ほかの利用者とハードウェアを共有できない場合。
Dedicated Instancesなし（割高）専用ハードウェア上でインスタンスを実行する（物理サーバーの配置管理はできない）。
オンデマンドキャパシティ予約なし特定の AZ で、必要なときに確実に起動できる容量を確保しておく。
🔑覚え方：処理の性質で選ぶ

中断してよい → スポット／長期間継続 → RI・Savings Plans／予測できない・短期 → オンデマンド／ライセンス持ち込み・規制対応 → Dedicated Hosts

⚠️間違えやすい点
  • 「中断できない重要な処理を最も安く」→ スポットは不適切（中断の可能性があるため）。長期なら RI か Savings Plans、短期ならオンデマンド。
  • 「既存のライセンスを持ち込みたい（BYOL）」→ Dedicated Hosts。Dedicated Instances と混同しないこと。
    BYOL（Bring Your Own License）＝保有しているソフトウェアの使用権をクラウド上で利用すること。

3. Auto Scaling と ELB：台数の自動調整と負荷分散

💡イメージで理解する

ELB は窓口の受付にあたります。到着した利用者を、対応可能な担当者（サーバー）へ順に割り振り、対応できない担当者（障害のあるサーバー）には割り振りません。

Auto Scaling は人員配置の管理者にあたります。混雑時には担当者を自動で増員し、閑散時には減員します。最小人数と最大人数もあらかじめ設定できます。

一方の AZ に障害が発生しても、ELB はもう一方の AZ の EC2 に通信を振り分け、Auto Scaling が不足した台数を自動で補います。これにより高可用性と伸縮性を両立できます。
Amazon EC2 Auto Scalingオートスケーリング
EC2 の台数を需要に応じて自動で増減する。異常のあるインスタンスを自動で置き換える機能も持つ。
主なスケーリング方式：ターゲット追跡（例：CPU 使用率を50%に維持）／スケジュール（例：毎朝9時に増加）／予測（過去の傾向から事前に増加）。
Elastic Load Balancing（ELB）ロードバランサー
受信した通信を複数のサーバーに振り分ける（負荷分散）。ヘルスチェックにより、異常のあるサーバーには通信を送らない。

🎯試験での問われ方
  • 「アクセス量の増減に応じて台数を自動で調整したい」→ Auto Scaling
  • 「複数の EC2 に通信を分散し、1台に障害が起きても停止しないようにしたい」→ ELB（＋複数 AZ）
  • 「URL のパスによって転送先を変えたい」→ ALB／「超高性能・固定 IP が必要」→ NLB

4. Lambda：サーバーレスなコード実行

AWS Lambdaラムダ
コードを登録しておくだけで、イベントの発生時に自動で実行される。サーバーの用意や管理は不要（サーバーレス）。実行回数と実行時間（ミリ秒単位）に応じて課金される。
💡イメージで理解する

EC2 は常時点灯している照明に近く、利用者がいなくても稼働している間は料金が発生します。Lambda は人感センサー付きの照明に近く、必要なときだけ動作するため、実行がなければ料金は発生しません。

イベント駆動：必要なときだけ処理が実行されるため、待機中のコストが発生しません。
⚠️間違えやすい点

Lambda の1回あたりの実行時間は最大15分です。数時間かかる処理には適さないため、EC2・Batch・Fargate などを使います。

5. コンテナ

コンテナは、アプリケーションとその実行に必要な要素を1つのパッケージにまとめたものです。

💡イメージで理解する

海上輸送のコンテナは、中身にかかわらず規格が統一されているため、どの船やトラックにも積載できます。IT のコンテナも同様で、開発環境と本番環境の差異による「手元では動くが本番では動かない」という問題を減らせます。

  • ECR＝ コンテナイメージ（コンテナの元になるテンプレート）を保管するレジストリ
  • ECS / EKS＝ コンテナの配置・起動・停止を管理する仕組み（オーケストレーション）
  • Fargate＝ コンテナを実行するサーバーを AWS が用意・管理する実行環境

6. その他のコンピューティングサービス

Amazon Lightsailライトセイル
月額定額で利用できる簡易的な仮想サーバー。サーバー・ストレージ・ネットワークが一式で提供される。「AWS の専門知識がなくても、小規模なサイトや WordPress を手軽に構築したい」→ Lightsail。
AWS Elastic Beanstalkビーンストーク
コードをアップロードするだけで、EC2・ELB・Auto Scaling などの環境を自動で構築する（PaaS）。「インフラを意識せずに Web アプリケーションを迅速に公開したい」→ Beanstalk。
AWS Batchバッチ
大量のバッチ処理を自動でスケジュール・実行する。必要な台数の計算資源を確保し、処理が終われば解放する（スポットインスタンスとの組み合わせに適する）。
AWS Outpostsアウトポスト
AWS のハードウェアを自社のデータセンターに設置し、AWS と同じサービスや API を利用できる。「データをオンプレミスに置いたまま AWS のサービスを使いたい」→ Outposts（ハイブリッド構成）。
🎯試験での問われ方（まとめ）
  • 「サーバーを管理したくない」「イベントを契機に実行したい」→ Lambda
  • 「コンテナを実行したいが、サーバーは管理したくない」→ Fargate
  • 「Kubernetes」→ EKS
  • 「コードをアップロードするだけで Web アプリケーション環境を自動構築したい」→ Elastic Beanstalk
  • 「月額定額・簡単に始めたい」→ Lightsail
  • 「自社のデータセンターで AWS のサービスを使いたい」→ Outposts

Auto Scaling と ELB の役割の違いを説明してください。
ELB は受信した通信を正常なサーバーに振り分ける（負荷分散・ヘルスチェック）。Auto Scaling は需要に応じてインスタンスの台数を自動で増減する。
ALB・NLB・GWLB はどのように使い分けますか。
ALB＝HTTP の内容（URL のパスなど）で振り分け（レイヤー7）。NLB＝TCP/UDP を超高速に処理、固定 IP（レイヤー4）。GWLB＝サードパーティのセキュリティ製品に通信を経由させる。
Lambda の特徴と、適さない処理を説明してください。
サーバー管理が不要で、イベントを契機に実行され、実行回数と実行時間に応じて課金される。1回の実行は最大15分のため、長時間の処理には適さない。
ECS・EKS・Fargate・ECR の違いは何ですか。
ECS＝AWS 独自のコンテナ管理、EKS＝Kubernetes のマネージドサービス、Fargate＝コンテナ向けサーバーレス実行環境、ECR＝コンテナイメージのレジストリ。
Lightsail・Elastic Beanstalk・Outposts はそれぞれどのような場合に使いますか。
Lightsail＝月額定額の簡易サーバー。Beanstalk＝コードをアップロードするだけで環境を自動構築。Outposts＝自社のデータセンターで AWS のサービスを利用。
