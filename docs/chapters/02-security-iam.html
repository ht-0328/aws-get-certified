第2章 セキュリティとIAM

セキュリティは CLF・SAA とも配点が最も大きい分野の一つです。AWS は設備と基盤を守り、利用者はデータ・権限・設定を守ります（責任共有モデル）。権限は IAM、攻撃の防御は Shield と WAF、脅威の検出は GuardDuty などです。

🧭この章で理解してほしいこと
  • 守る責任は AWS と利用者で分担する：AWS は器、利用者は中身（責任共有モデル）
    • AWS が守る（Security OF the Cloud）
      • データセンターの建物・電源・物理的な警備
      • 物理サーバー・仮想化基盤・基盤ネットワーク
    • 利用者が守る（Security IN the Cloud）
      • データ、IAM のアクセス権限
      • アプリケーションのコード、セキュリティグループの設定
      • EC2 の OS の更新・パッチ
    • マネージドなサービスほど AWS の範囲が広い
      • RDS（データベース）のエンジン、Lambda（コード実行）の OS のパッチは AWS
      • データとアクセス権限は、どのサービスでも利用者
    • 賃貸なら、AWS は建物と共用部、利用者は自室の施錠と中身
  • 権限は IAM で決める：人にはグループ経由でポリシー、サービスにはロール
    • IAM：誰が AWS を使え、どの操作ができるかを管理する。無料
    • リージョンに属さないグローバルサービス
    • ユーザー：1人（または1つのアプリ）に1つの認証情報。共有しない
    • アクセスキー：CLI・SDK 用の認証情報。アクセスキー ID とシークレットの組
    • グループ：ユーザーの集合。ポリシーはグループに付ける。入れ子は不可
    • ポリシー：JSON で書く許可・拒否の規則
      • 明示的な拒否（Deny）が最優先
      • どこにも許可がなければ拒否（暗黙の拒否）
    • ロール：必要なときだけ引き受ける一時的な権限
      • EC2・Lambda などのサービスや、別アカウントの利用者に付ける
      • 有効期限付きの認証情報が自動で発行される
    • 「EC2 から S3（ストレージ）へ」はアクセスキーを置かず、IAM ロールを付ける
  • ルートユーザーは日常で使わない：原則は最小権限・MFA・ルートを使わない
    • ルートユーザー：アカウント作成時に作られる全権限のユーザー
      • MFA を設定して厳重に保管し、アクセスキーは作らない
      • 管理者全員で共有するのは誤り。1人1つの IAM ユーザーを作る
    • ルートユーザーでしかできない操作
      • アカウントの解約
      • サポートプランの変更
      • ルートユーザーのメールアドレスなどアカウント設定の変更
    • 最小権限：業務に必要な範囲だけの権限を付ける
    • MFA：パスワード（知っているもの）＋認証アプリ（持っているもの）
  • 複数アカウントは Organizations：SCP は上限を決めるだけで権限は付与しない
    • Organizations：複数のアカウントを1つの組織として管理する
      • 一括請求：請求をまとめ、ボリューム割引を受けやすくする
      • SCP：アカウント単位で使えるサービスやリージョンを制限する
      • IAM で許可していても、SCP で禁止された操作はできない
    • IAM Identity Center：1回のサインインで複数のアカウントに入れる（SSO）
    • Identity Center は Microsoft Entra ID などの ID 基盤と連携できる
  • 鍵・パスワード・証明書は専用のサービスで管理：名前の英単語がそのまま役割
    • KMS（Key）：暗号鍵の作成・管理
      • S3（ストレージ）・EBS（ディスク）・RDS（データベース）と連携できる
      • 鍵の使用履歴は CloudTrail に残る
    • CloudHSM（Hardware）：専用機器で鍵を利用者だけが管理。厳格な規制向け
    • Secrets Manager：DB のパスワードなどを保管し、自動でローテーション
      • Parameter Store も値を保存できるが、自動ローテーションはこちら
    • ACM（Certificate）：SSL/TLS 証明書を発行し自動更新する
    • ELB・CloudFront で使うパブリック証明書は無料
  • DDoS は Shield、Web 攻撃は WAF：Shield は量、WAF は内容を防ぐ
    • Shield Standard：一般的な DDoS（大量の通信で止める攻撃）を防ぐ。無料で自動適用
    • Shield Advanced：大規模・高度な DDoS 向け。有料
      • 24時間365日の専門チーム（SRT）が支援する
      • 攻撃に伴う利用料の増加を補償する
    • WAF：SQL インジェクション・XSS など Web への攻撃を遮断する
      • 特定の IP・国・不審なリクエストを規則で遮断する
      • CloudFront（配信）・ALB（負荷分散）・API Gateway（API の窓口）に適用する
    • Shield は防波堤、WAF は入口の検査
  • 脅威対応は「検出 → 集約 → 調査」：検出するサービスは遮断しない
    • GuardDuty：ログを機械学習で分析して脅威を検出する
      • CloudTrail（操作の記録）・VPC フローログ（通信の記録）・DNS ログを分析する
      • 「誰が操作したか」の記録は CloudTrail。GuardDuty は分析する側
    • Inspector：EC2・コンテナイメージ・Lambda の脆弱性を検査する
    • Macie：S3 の個人情報（PII）など機密データを検出する
    • Secrets Manager（パスワードの保管）と混同しない
    • Security Hub：各サービスの検出結果を1か所に集約する
    • Detective：検出された問題の根本原因と経緯を調査する
    • 遮断は WAF やセキュリティグループの役割
  • 監査レポートは Artifact、アプリの利用者認証は Cognito
    • Artifact：AWS の第三者監査レポート（ISO・SOC・PCI DSS）を取得する
    • Cognito：自社アプリの会員登録・サインイン・外部 ID 連携
    • IAM は「AWS を操作する人」、Cognito は「アプリを使う一般の利用者」

読み終えたら、本文を見ずに各項目を自分の言葉で説明できるか確かめてください。

1. 責任共有モデル：誰が何を守るのか

クラウドでは、セキュリティの責任を AWS と利用者で分担します。この考え方を責任共有モデルといいます。

💡イメージで理解する

賃貸マンションに置き換えると分かりやすくなります。AWS は建物の所有者として、建物の構造・共用部の入退室管理・設備の保守（＝データセンター、物理機器、基盤ネットワーク）に責任を負います。

利用者は入居者として、自室の施錠、合鍵を誰に渡すか、室内に置いた資産（＝データ、設定、認証情報）の管理に責任を負います。

🔑覚え方：「クラウドの」と「クラウドの中」

AWS ＝ Security OF the Cloud（クラウドそのもののセキュリティ）
利用者 ＝ Security IN the Cloud（クラウド上に置いたもののセキュリティ）

「AWS は器、利用者は中身」と整理しておくと判断しやすくなります。

2. IAM：誰に何を許可するか

IAMアイアム／Identity and Access Management
AWS を誰が利用でき、どの操作を許可するかを管理するサービス。無料。特定のリージョンに属さないグローバルサービスです。
💡イメージで理解する

オフィスの入館管理に置き換えると、IAM の各要素は次のように対応します。

  • ユーザー＝ 社員証を持つ個々の従業員。
  • グループ＝「経理部」「開発部」などの部署。部署単位で入館権限を設定すれば、人の増減に容易に対応できる。
  • ポリシー＝「この部署はサーバールームに入室可」といった権限の規定。
  • ロール＝ 必要なときだけ発行される一時入館証。保持している間だけ権限が有効になり、人だけでなく EC2 などの AWS サービスにも付与できる。

IAM ユーザー個人（または1つのアプリケーション）用の認証情報1人につき1ユーザー。共有しない。
IAM グループユーザーの集合グループにポリシーを付与すると管理が容易。グループを入れ子にはできない。

アクセスキーCLI・SDK などプログラムからアクセスするための認証情報。アクセスキー ID とシークレットアクセスキーの組人のコンソール操作はパスワード（＋MFA）。EC2 上のプログラムにはキーを置かず、IAM ロールを使う。

ルートユーザーでしか実行できない操作

ルートユーザーは権限が強すぎるため、通常の作業は IAM ユーザー（または IAM Identity Center）で行います。ただし、次のようなアカウント自体に関わる操作はルートユーザーでしか実行できません。

  • アカウントの解約（閉鎖）
  • サポートプランの変更
  • ルートユーザーのメールアドレスなど、アカウント設定の変更

セキュリティの基本原則

🔑覚え方：IAM の3原則「最小・二重・使わない」
  1. 最小権限の原則：業務に必要な範囲だけの権限を付与する。
  2. 二重の本人確認＝ MFA：パスワードに加えて認証アプリなどを組み合わせる。
    MFA（多要素認証）＝「知っているもの（パスワード）」「持っているもの（スマートフォン等）」など、種類の異なる要素を組み合わせて本人確認する方式。
  3. ルートユーザーは使わない：ルートユーザーのアクセスキーも作成しない。

⚠️間違えやすい点
  • 「EC2 から S3 にアクセスさせるため、アクセスキーを EC2 に保存する」→ 誤り。正しくは IAM ロールを EC2 に付与する。
  • 「管理者全員でルートユーザーを共有する」→ 誤り。1人1つの IAM ユーザー（または Identity Center のユーザー）を作成する。

3. 複数アカウントの管理

組織の規模が大きくなると、「開発用」「本番用」「経理用」など、AWS アカウントを複数運用するのが一般的です。これらを一元管理するためのサービスがあります。

AWS Organizationsオーガニゼーションズ
複数のアカウントを1つの組織として一元管理する。請求をまとめる一括請求や、SCP によるアカウント単位の操作制限が可能。
IAM Identity Centerアイデンティティセンター（旧 AWS SSO）
1回のサインインで複数のアカウントやアプリケーションにアクセスできる仕組み（シングルサインオン）を提供する。Microsoft Entra ID などの既存の ID 基盤とも連携できる。
💡イメージで理解する

Organizations を企業グループ、各アカウントを子会社とすると、SCP（サービスコントロールポリシー）はグループ全体の社内規程にあたります。子会社の管理者（IAM）が許可していても、規程で禁止されている操作は実行できません。SCP は「実行できる操作の上限」を定めるだけで、権限を付与するものではありません。

🎯試験での問われ方
  • 「複数アカウントの請求をまとめたい／ボリューム割引を受けたい」→ Organizations の一括請求
  • 「特定のアカウントで、特定のサービスやリージョンを使用禁止にしたい」→ SCP
  • 「従業員が1回のサインインで複数アカウントにアクセスできるようにしたい」→ IAM Identity Center

4. 暗号鍵と機密情報の管理

データを暗号化するには鍵が必要です。ここでは、その鍵やパスワードなどの機密情報を安全に管理するサービスを扱います。

「専用のハードウェア」「鍵を利用者だけで管理」→ CloudHSM。

5. 外部からの攻撃への対策：Shield と WAF

インターネットに公開したシステムは、さまざまな攻撃の対象になります。代表的なものが DDoS 攻撃です。

💡イメージで理解する

Shield は防波堤にあたります。押し寄せる大量の通信（DDoS）を受け止め、システムに到達させないようにします。

WAF は入口での検査にあたります。個々のリクエストの内容を規則に照らして確認し、悪意のあるものを通しません。

6. 脅威の検出と調査

名称が似ており混同しやすい分野です。「何を対象に、何をするサービスか」で分類して整理します。

💡イメージで理解する

組織のセキュリティ部門の役割分担に置き換えると、次のように対応します。

  • GuardDuty＝ 監視担当。ログを継続的に分析し、不審な挙動を検出して通知する。
  • Inspector＝ 診断担当。EC2 やコンテナなどに脆弱性がないかを検査する。
  • Macie＝ データ保護担当。S3 に個人情報などの機密データが含まれていないかを検出する。
  • Detective＝ 調査担当。問題が発生した後に、原因と経緯を分析する。
  • Security Hub＝ 統括部門。各サービスの検出結果を一元的に集約し、全体の状況を評価する。
検出系サービスの結果は Security Hub に集約される

🔑覚え方：「検出 → 集約 → 調査」の流れで並べる

検出：GuardDuty（脅威）・Inspector（脆弱性）・Macie（機密データ）→ 集約：Security Hub → 調査：Detective

Macie は「Macie ＝ S3 内の M（My）個人情報を探す」と結びつけると区別しやすくなります。

⚠️間違えやすい点

GuardDuty は脅威を検出するサービスであり、攻撃を遮断するものではありません。遮断は WAF やセキュリティグループなどが担います。また、「誰がどの操作をしたかの記録」は CloudTrail（第7章）の役割で、GuardDuty はその記録を分析する側です。

「S3 の機密データ（個人情報）を自動で検出・分類したい」→ Macie。Secrets Manager はパスワードなどの秘密を保管するサービスで、データの検出はしません。

7. その他のセキュリティサービス

AWS Artifactアーティファクト
AWS が取得した第三者監査レポート（ISO・SOC・PCI DSS など）をダウンロードできるポータル。「AWS の法令・規則への準拠（コンプライアンス）を示す資料が必要」→ Artifact。
監査＝外部の専門家が、規程や基準への準拠状況を検証すること。
Amazon Cognitoコグニート
自社で開発するアプリケーションの利用者向けの認証機能（会員登録・サインイン・外部 ID 連携など）を提供する。IAM は「AWS を操作する人」、Cognito は「アプリケーションのエンドユーザー」を対象とする。
🎯試験での問われ方（まとめ）
  • 「コンプライアンスレポートを入手したい」→ Artifact
  • 「モバイルアプリに会員登録・サインイン機能を追加したい」→ Cognito
  • 「DDoS 対策を追加費用なしで」→ Shield Standard／「専門チームの支援が必要」→ Shield Advanced
  • 「SQL インジェクションを防ぎたい」→ WAF
  • 「暗号鍵を管理したい」→ KMS／「専用ハードウェアで管理したい」→ CloudHSM

🧠 想起練習

本文を見ずに答えを思い出してから、各項目を開いて確認してください。

責任共有モデルにおける AWS と利用者の責任範囲を、一言で説明してください。
AWS は「クラウドの（OF）」セキュリティ＝基盤。利用者は「クラウドの中の（IN）」セキュリティ＝データ・設定・アクセス権限。
EC2 と RDS で、OS やデータベースエンジンのパッチ適用を担うのはそれぞれ誰ですか。
EC2 は利用者。RDS は AWS（マネージドサービスのため）。
IAM のユーザー・グループ・ポリシー・ロールの役割をそれぞれ説明してください。
ユーザー＝個人の認証情報、グループ＝ユーザーの集合、ポリシー＝許可・拒否の規則、ロール＝サービスや他アカウントが一時的に引き受ける権限。
EC2 から S3 にアクセスさせる正しい方法は何ですか。
EC2 に IAM ロールを付与する（アクセスキーを保存しない）。
IAM の3原則を挙げてください。
最小権限の原則／MFA の使用／ルートユーザーを日常的に使わない（最小・二重・使わない）。
ルートユーザーでしか実行できない操作の例を2つ挙げてください。
アカウントの解約、サポートプランの変更（ほかに、ルートユーザーのメールアドレスなどアカウント設定の変更）。
SCP は権限を付与するものですか。
付与しない。Organizations 配下のアカウントで実行できる操作の上限を定めるだけである。
Shield と WAF の違いは何ですか。
Shield は DDoS 攻撃（大量の通信）を防ぐ。Standard は無料・自動、Advanced は有料で専門チームの支援付き。WAF は SQL インジェクションなど、Web リクエストの内容を検査して攻撃を防ぐ。
GuardDuty・Inspector・Macie・Security Hub・Detective の役割をそれぞれ説明してください。
GuardDuty＝脅威の検出、Inspector＝脆弱性の検査、Macie＝S3 の機密データの検出、Security Hub＝検出結果の一元化、Detective＝原因の調査。
パスワードを自動でローテーションしたい場合のサービスは何ですか。証明書の場合は何ですか。
Secrets Manager。証明書は ACM（自動更新）。
AWS の監査レポートを入手するサービスと、アプリケーション利用者の認証機能を提供するサービスは何ですか。
監査レポートは AWS Artifact。認証機能は Amazon Cognito。
